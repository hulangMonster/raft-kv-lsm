
# M6.10.1 BLOCKER — lsm 引擎 flush/Close 竞态会留下「有 *.sst、无 MANIFEST」的不可恢复库

- 发现于：M6.10.1「>64 MiB 载荷分块原子 restore」实现后的重开验证。
- 性质：**lsm 引擎侧缺陷**（`~/lsm-kv` @ f06a44d）。在 M6 原约束「不改 lsm 仓库」下，raft-kv 侧无法稳妥修复。
- 影响面：**不止 M6.10.1** —— 既有 `LsmLogStore`（M6 日志层）同样中招；任何 memtable 超过 `write_buffer_size`（默认 4 MiB）并在 flush 窗口 Close / kill -9 的负载都可能启动失败。

## 1) 最小复现（纯 lsm 公共 API，不经过任何 raft-kv 代码）

源码：`docs/raw/m6.10.1-raw_lsm2.cpp`。步骤：Open → 2 次 `WriteBatch::Put`（每次 2 MiB，合计 4 MiB = 默认 `write_buffer_size`）→ `Close()` → 重新 `Open()`。

原始输出（`docs/raw/m6.10.1-raw_lsm-matrix.txt`）：

| 场景 | reopen |
|---|---|
| 2 MiB ×2，立即 Close | **FAIL**：`VersionSet::RecoverManifest: 元数据缺失但目录非空（*.sst 或 MANIFEST-*）` |
| 2 MiB ×2，Close 前 sleep 1500 ms | OK |
| 2 MiB ×4 | OK |
| 2 MiB ×2，`write_buffer_size=256 MiB`（不触发 flush） | OK |
| 2 MiB ×2，写间穿插 Get | **FAIL** |

Close 后目录内容（`docs/raw/m6.10.1-raw_lsm-files.txt`）：

   000001.log 2097627
   000002.log 2097627
   000003.sst 2097375
   LOCK 0

→ **有 SST、有完整 WAL、完全没有 `MANIFEST-*`**。数据本可由 WAL 重放，但恢复入口在 MANIFEST 缺失时直接拒绝。

## 2) 既有 `LsmLogStore` 同样中招（`docs/raw/m6.10.1-lsmstore.txt`）

```
# LsmLogStore::append(3 条 x 5 MiB) 返回成功；析构 Close 后重建：
terminate called after throwing an instance of 'std::runtime_error'
  what():  LsmLogStore: lsm DB::Open(.../raft-lsm) failed:
            Corruption: VersionSet::RecoverManifest: 元数据缺失但目录非空（*.sst 或 MANIFEST-*）
Aborted (core dumped)
```
（3 条 × 2 MiB 未复现；× 5 MiB 复现 ⇒ 与是否触发 memtable flush 一致。）

## 3) 根因（lsm 源码定位，未做任何修改）

- `src/db_impl.cpp` `PersistentDBImpl::Close()`：置 `bg_stop_` → join flush 线程；被中断的 flush **放弃** immutable（`flush_stats_.immutables_abandoned += immutables_.size()`，注释「§6.5 ... 必须放弃剩余 immutables 并退出」）。若 flush 已写出 `*.sst` 但 **尚未提交 MANIFEST edit**，磁盘就留下孤儿 SST。
- `src/version_set.cpp` `RecoverManifest()`（约 816-822 行）：CURRENT/MANIFEST 缺失但目录存在 `*.sst`/MANIFEST-* 时**按设计拒绝自动修复**（安全阀，防静默丢数据）⇒ 直接 Corruption。
- 即：写 SST 与提交 MANIFEST 不是一个可中断安全的序列；Close/kill -9 落在中间窗口即不可恢复。
- 引擎**没有**生产可用的 `DB::Flush()`：`src/db_impl.h:296` 注释明确「设计 §8.7 E4 不新增公共 `DB::Flush()`；小 write_buffer_size 也无法冲刷『最后一个 memtable』」，只有 `ForceFlushForTest()`。

## 4) 为什么 raft-kv 侧无法稳妥绕过

- **调大 `write_buffer_size`**（不触发 flush）不可行：WAL 仅在 flush 时轮转/回收（lsm §6.6.1），更新密集型负载下 WAL 无界增长。
- **sleep/轮询等 flush 完成**：纪律禁止「用 sleep 换绿」，且生产中不可靠。
- **删孤儿 `*.sst`**：跨仓改 lsm 文件；且无法一般性证明 WAL 一定覆盖该 SST 的数据。

## 5) 建议（需父代理裁决，因 M6 原约束「不改 ~/lsm-kv」）

1. **首选：修 lsm 引擎**（`~/lsm-kv` 新 commit）：
   a. flush 改为「SST 先写 `*.sst.tmp` → fsync → 提交 MANIFEST edit → rename 为 `*.sst` → fsyncDir」；或
   b. `Close()` 不放弃在途 flush（等它完成 MANIFEST 提交再退出）；若必须放弃，则删除该孤儿 SST（数据仍在 WAL）；
   c. `RecoverManifest()` 对「无 MANIFEST + 有 SST + WAL 完整」的库，先删孤儿 SST 再按空库 + WAL 重放，并计数 `orphan_sst_removed`。
2. 修好后把 `~/raft-kv-lsm` 的 pin 换到新 sha，再跑 M6.10.1 的 >64 MiB restore / apply-reopen / kill-mid-restore 全套。
3. 在此之前 **M6.10.1 不应宣布完成**；该缺陷同时应作为 M6 已知风险登记（任何 >write_buffer_size 的日志负载在 kill -9/flush 窗口都可能启动失败）。
